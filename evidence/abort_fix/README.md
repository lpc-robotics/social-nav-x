# Premature-abort corrective evidence

This directory records the 2026-09-17/18 investigation of a live MPC
`NavigateToPose` goal that stopped before reaching its target and returned
`ABORTED`.

## Root cause and accepted regression evidence

- `online_root_cause.json` is a read-only snapshot of the user's original
  release `20260916-4ff2edd` in ROS domain 51. It correlates repeated
  `measured braking trajectory failed swept HuNav check after MPC solve
  rejected: Maximum_WallTime_Exceeded` controller exceptions with FollowPath
  and NavigateToPose aborts. GoalChecker did not declare a false arrival.
- `forced_overlap_recovery.json` is the accepted focused regression. A human
  is placed on the robot for longer than the controller's five-cycle failure
  limit. The watchdog begins zero output in 0.03745 s, emits no nonzero command
  during overlap, the action remains active, and the same goal succeeds after
  the overlap is removed (`action_status=4`).
- `forced_overlap_progress_checker.json` repeats that regression with the
  SafetyAwareProgressChecker loaded by controller_server. It again keeps the
  action active through 20 recoverable stops and reaches the same goal after
  the overlap is removed.

The controller therefore treats a transient dynamic safety conflict as a
recoverable zero-command decision. Input, TF, path, static-map and malformed
data errors remain ordinary controller failures.

## Superseded or rejected exploratory runs

- `forced_overlap_recovery_rejected_startup_race.json` sent its goal during a
  lifecycle activation race and was preempted. It is retained and is not used
  as evidence.
- `six_behaviors_arrival_attempt1.json` and
  `six_behaviors_arrival_attempt2.json` both reached the goal with
  `action_status=4`. Their old probe marked them false only because its 0.05 m
  sampling-alignment ceiling predated the validated 0.8 m/s speed profile; the
  measured bounds were 0.05647 m and the conservative human clearances were
  about 0.522 m. They are supporting action-level evidence, not accepted P4
  reports.
- `endurance_5min.json` exposed a separate progress-checker error: the inherited
  0.5 m movement radius could exceed the remaining distance of short return
  legs and produced one `FailedToMakeProgress` abort.
- `endurance_5min_corrected.json` used the corrected 0.05 m radius and 120 s
  allowance and recorded zero aborted goals. It is not a formal pass because
  the old harness cancelled one still-active goal after 180 wall seconds.
- `endurance_30min_rejected_progress.json` is the rejected first formal start.
  It proved that the standard SimpleProgressChecker still counted dynamic
  safety waits and aborted the second return goal despite the 0.05 m/120 s
  parameters. The run was stopped once its gate had irreversibly failed.
- `endurance_30min_rejected_rotation_progress.json` is the rejected second
  formal start. Safety waits were paused and eight goals succeeded, but the
  first SafetyAwareProgressChecker revision counted translation only. Near the
  XY goal tolerance it failed to recognize terminal yaw progress. The accepted
  revision also treats 0.1 rad of rotation as progress.
- `six_behaviors_persistent_block.json` holds an intentionally non-passing
  run in which the fixed six-behavior layout kept the robot at its start for
  the full 360 wall seconds. Nav2 did not abort the action; the probe timed out.
  This is a persistent-block boundary observation, not an arrival result.

## Formal replacement endurance

`endurance_30min_corrected.json` is generated by the corrected gate. It uses a
600 s wall-clock per-goal limit so that the harness cannot cancel a goal before
the 120 s ROS-time progress window when Isaac is running below real time. The
report is accepted only when at least ten goals succeed and both
`aborted_goal_count` and `timed_out_goal_count` are zero. It also reads the
actual progress-checker parameters from the live controller server.

Launch logs are intentionally ignored by Git. Every JSON report binds its
source/config hashes, ROS domain, GPU snapshot and corresponding local log
path where applicable.
